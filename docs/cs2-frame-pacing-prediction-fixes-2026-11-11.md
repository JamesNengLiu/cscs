# CS2 出帧时机、延迟预测与联机恢复修复

本轮只改独立 CS2 验证版，基于 `0e0c1f1` 合入呈现调度、延迟预测、联机恢复和资源加载补丁，并补齐集成验证发现的边界问题。弹道、后坐力、移动规则、碰撞、1.0 源码均未改动；提交与推送仅限 `codex/cs2`，不合回 `main`。

## 1. 满帧却顿挫：出帧调度对照

**现象。** 匪家至 A 门黄车一带，游戏帧率稳定 75、主线程约 4ms、显卡约 4–6ms、位置修正为零，画面却间歇性一顿一顿；与画质无关，刷新页面后时有时无。

**作者给出的定位。** 补丁作者依据其 Chrome 156 trace，将问题归因于合成器的两种提交节奏；本次合入不把这项定位自动等同于当前环境的已复现结论。其说明为：Chrome 合成器有两种状态，页面无法观察或选择：一种在垂直同步信号到来后立刻提交上一帧；另一种等页面的 `requestAnimationFrame` 回调执行完再提交。后一种状态下，约 4–5ms 的帧主体把提交时刻推到距离显示器合成截止点 1ms 左右，帧在“赶上”和“错过”之间来回跳：页面每帧都按时产出，但部分帧晚一拍上屏、下一帧被挤掉。

补丁作者报告的测量（Chrome 156、Apple M1 Pro、外接 1920×1080 @ 75Hz，按普通方式启动的浏览器，Chrome 合成器 trace；下表不是本次合入时重新测得的数据）：

| 场景 | 合成帧提交时刻（距上次刷新） | 晚一拍上屏 |
| --- | ---: | ---: |
| 用户手动复现“不卡” | 约 7.9ms | 22 秒内 0 帧 |
| 用户手动复现“很卡” | 约 11.9–12.5ms | 3.4–3.7 帧/秒，突发 11–22 帧/秒 |
| 自动化、轻场景、旧方式 ×3 | 11.9ms | 1.8 / 3.1 / 5.7 帧/秒 |
| 自动化、轻场景、新方式 ×3 | 7.8–8.1ms | 0 / 0 / 0 |

作者从其 trace 读出的截止点约在刷新后 11.2–11.5ms：此前提交的帧下一拍上屏，此后的多等一拍。

**修复。** 新增 `public/cs2-frame-scheduler.js`。`requestAnimationFrame` 回调登记真实时间戳并投递 `MessageChannel` 任务，帧主体在另一个任务中执行。补丁作者在上述环境观察到较早且更稳定的提交时机；但 `MessageChannel` 不提供合成器提交屏障，也不保证固定提交时刻或零额外延迟。默认 `deferred`，`?frame=inline` 可回退作对照；诊断与导出 JSON 的 `frameScheduling` 会报告实际方式、排队延迟和丢弃计数。端口任务排队超过 50ms 或页面隐藏时丢弃旧任务、等待新 rAF，不以当前墙钟伪造旧帧时间。

**边界。** 帧主体与显卡执行的总预算比“不等页面”的原方式少约 0.8ms（一次样式／提交的时间）。重场景下（主线程约 6ms、显卡 P95 约 10ms）两种方式都仍有零星晚帧，自动化测得新方式 0–0.5 帧/秒、原方式 0–1.0 帧/秒。这是软件呈现反馈，不是物理屏幕扫描或输入到光子的认证；其他浏览器、显卡和刷新率未测。

## 2. 有延迟时本地预测被关闭

`0e0c1f1` 的移动时间线用客户端时钟给每个输入样本打“预计执行 tick”的标签，但时钟从最近收到的服务器 tick 起步，比样本真正执行的 tick 早一个往返延迟加排队深度，于是未确认样本全部被当成“时间已过”而不回放。只有跳、蹲、静步边沿被确认时标签才会校正，而且只能向前。

**修复。** 服务器在快照里私有地公布“最新已执行输入”所在的物理 tick（`movementAppliedTick`，与 `lastAppliedInputSeq` 成对）。客户端每次收到新的已执行确认，都按这对实测值双向校正待确认样本和时钟（`alignAppliedMovement`）。时钟复位后、首次校正前的标签视为临时值，按“每 tick 一条”的顺序全部回放（`unanchored-replay`）。旧服务器没有该字段时行为不变。

离线模拟（真实游戏内核加真实对账代码，逐 tick 确定性）：

| 单程延迟 | 修复前预测误差 | 修复后 |
| --- | ---: | ---: |
| 0 tick | 0 | 0 |
| 3 tick（往返 100ms） | 中位 0.27m，最大 0.31m | 0 |
| 6 tick（往返 200ms） | 中位 0.56m，最大 0.61m | 0 |

预测误差指“客户端采样第 n 条输入后的位置”与“服务器真正执行第 n 条后的位置”的距离。

## 3. 队列变短后每次对账都多插空转帧

标签只能向前，服务器队列变短后标签停在旧深度，之后每次对账都插入服务器并不会执行的空转步。模拟中表现为每次对账 5 个空转 tick、预测速度为权威的 0.91、持续 0.15m 误差。双向校正后三项均为 0。

## 4. 一次中断变成整条命的输入延迟

服务器原先每 tick 只执行一条输入，仅清理超龄或缺号样本；仍未超龄的持续积压可能长期不消退。作者的 400ms 上行中断实验中，可靠补发送达 24 条旧输入后，输入延迟持续约 26 tick。

**修复。** 队列深度超过 `INPUT_BACKLOG_LIMIT`（4）时，每 tick 至多额外退役一条按键及方向轴均与前后相同的纯移动样本，走原跳过确认路径，每 tick 仍只有一次物理步。射击、使用，以及被待执行动作栅栏引用的样本不参与裁剪，跳蹲静步和方向轴边沿保留。纯移动时允许合并较旧的鼠标朝向、采用后继样本的角度以降低延迟，不承诺重现每个旧转向角；关键射击和操作样本不这样合并。服务器仅向本人公布有限的队列序号、受保护序号和最后执行输入；客户端只对明确已排队且完整持有的前缀镜像裁剪，在途输入不当作已排队。名义样本标签与真实预测物理 tick 分开维护，预测标记不会删除输入的 ACK、武器顺序及重发责任。受保护输入密集时不强求队列始终小于 4。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 中断结束很久之后的输入延迟 | 26 tick | 5 tick（2 tick 传输 + 队列 ≤4） |
| 恢复期间单次最大位置修正 | — | 作者版本约 0.51m；合入版保守镜像 CPU 圈转实验约 0.746m |

## 5. 资源加载超时会让整个加载器失效

单个任务 45 秒超时会终止解压线程并永久关闭加载器。现在超时是“无进度时限”：线程每 250ms 以内最多上报一次解码进度并重置计时，持续产生新增解码字节的任务不因总时长超过 45 秒而失败；仅网络仍有传输而解码没有推进，不保证能避免停滞超时；停滞的任务只让自己失败并取消，名额保留到线程确认；线程在宽限期内不确认才被替换，排队和后续任务在新线程继续；连续替换超过 3 次且期间没有任何任务成功才关闭。

## 6. 大幅恢复时镜头长时间偏离真实位置

平滑修正的容许距离此前放宽到 8m，静止时以 2.5m/s 收回，镜头可偏离权威位置三秒以上，而子弹从权威位置射出。保留原有 8m 绝对上限及同生命、短中断和显式瞬移的边界，改为限制持续时间：收回速度不低于“本次恢复的最大偏移 ÷ 0.5 秒”。1.25m 以内的普通修正速度不变；8m 偏移约 0.5 秒回到半米以内。

## 合入时补充的正确性边界

- 新的可信执行锚优先于旧边沿序号推算，避免退役后按序号差重新插入空转步；名义标签与物理时钟分别提交。
- 服务器与客户端镜像共同保护射击、使用及动作栅栏；有限队列按退役和模拟共同减少深度。
- 新回合、死亡、非活跃状态和清输入时同步清除恢复峰值，避免继承上一生命的大修正速度。
- 严格 650ms 双向断流对照复现了第二次执行锚校正与已有偏移相抵、却因原 0.5m 阈值清零缓冲的硬跳。现在只有已授权恢复、误差不超过旧偏移、合成偏移不增长且旧偏移仍在 8m 内时，才保留这个缩小中的偏移；同方向扩大、跨越整个包络、生命变化、显式瞬移及长中断不因此获得新许可。权威位置、执行锚、物理和射击源点不改。
- 解码进度严格递增才重置期限；补充并发线程替换、迟到回包及预算测试。
- 浏览器性能夹具观察真实帧主体入口和出口，不能再依赖 RAF 回调名为 `frame`。

原有 2703 项是作者提供的补丁验证结果。合入后的实际测试数量、当前浏览器条件和呈现反馈应以本次本机验证收据为准；单元测试不认证合成器或物理屏幕时序。服务启停、提交与推送分别遵循用户授权。

| 方式 | 三轮帧主体频率（Hz） | 三轮 CPU P95（ms） | 三轮 GPU 查询 P95（ms） | 三轮相邻已捕获显示槽内容重复 |

| inline | 75.00 / 75.00 / 74.99 | 5.9 / 6.0 / 5.9 | 7.08 / 7.15 / 7.11 | 0 / 92 / 97 |
| deferred | 75.01 / 75.00 / 74.99 | 6.0 / 6.0 / 6.0 | 6.74 / 6.46 / 6.58 | 0 / 0 / 0 |

本机受控条件下，结果支持 deferred 改善“满帧但内容重复”的呈现节奏；inline 第一轮也正常，不能声称每次必现。帧主体入口相对 rAF 时间戳的综合年龄 P95 约从 0.3ms 增至 0.6ms，该值包含 rAF 交付和任务调度，不是纯端口排队或物理输入延迟。SCK 采样缺口独立记录（各轮 0–2 次），未观测到的源帧不算成画面重复或物理掉帧。此测试覆盖渲染呈现，不替代实物鼠标、真实移动物理、多机联机或物理扫描时序验证；同用的条码也可能影响合成行为。`?frame=inline` 继续保留回退能力。


补充对同页两臂共同观测到的同一源帧 ID 做内容年龄配对：用原生单调时钟的显示槽时间差减去帧后 CPU 观察时刻差，deferred 相对 inline 的三对中位差约 **−0.33ms / +12.63ms / +12.73ms**。后两对提示稳定性可能以约一个 75Hz 槽的内容新鲜度为代价；第一对接近相同。该值来自已观测 ID 子集、两种单调时钟的差分，起点不是 GPU 完成、终点不是物理扫描，也不等于鼠标到屏幕延迟。时钟漂移和采样偏差未获硬件标定，因此它是需要保留的取舍证据，不能把补丁描述成所有状态下既更稳又零额外延迟。
