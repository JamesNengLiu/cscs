# 匪家至 A 门黄车整段负载与弹孔延迟排查

本轮确认了一个高优先级的射线查询性能缺陷，补齐正确黄车区域及多人负载对照；远程机器“换弹后弹孔继续补出”的唯一原因仍待现场采样。未修改弹道参数、命中算法、移动、网络传输或 1.0，也未重启现有服务。客户端仅增加默认关闭的射击诊断入口。

## 地点与场景负载

本次终点是 T 侧 A 门外黄橙色车，车体中心 runtime 约 `(-1.542, .810, 16.879)`，Source 约 `(664.53, -60.71, 31.88)`，原顶点 tint 为 RGB(210,127,45)。它不是之前 Source(1700,2050) 附近的 A 长蓝车。

已从真实 PHYS 确认八处合法身体站位，顺序覆盖坡上、坡中、坡下、街道转角、A 门外、黄车前、黄车旁与门口。诊断使用同机 Chrome157 / Metal、1920×913、DPR1 的后台浏览器，采样由脚本控制；10 人负载是一个浏览器加九个真实协议 peers，实际渲染九个加权原生角色与 AK/M4，不是十台物理设备。

九个原生人物和步枪带来约49.5万额外三角形、63 draw候选及63个独立骨骼 palette。现有人物调度只有视锥，没有墙体/PVS遮挡或距离 LOD。测量结束后的一次人物中心射线 proxy 中，黄车旁与门口有9/9个人物中心被世界遮住但仍被调度；这不是逐像素遮挡证明，不能用单个中心点直接隐藏敌人。

真实坡段 CPU/PVS 回放另记录到一次变化可上传约3.38MB索引前缀、重新分配约20.44MB orphan容量。贴图 `pump` 会在两个 runtime.update 入口被调用，每次还可能处理多个材质 variant；首次高 mip 上传与 orphan/人物负载应分开预算。当前 GPU query 不涵盖此前的全部上传工作，不能只据 GPU 查询排除 driver 上传卡顿。

本机后台对照未复现该整段持续低帧；约60Hz的软件回调、短样本和加载温度差异不能作为远程设备流畅性或前台75Hz认证。首次视区帧未等待 remaining=0，记录了队列/下载量，但1人与10人的各帧加载状态仍须匹配后比较，不能直接归因所有差值。observer P99约0.1–0.2ms；LOS查询仅在停止测量后执行，未把人数相关射线开销混进帧回调。

原1/10人父测试在完成八个有效1人case后，因测试脚本给尚未原生生成的late-join玩家买枪失败。未更改失败父收据；修正为原生begin/spawn、真实购区buy/equip后，另一次完整10人八站全部完成。

## 确定的服务器查询热点

当前开火是 hitscan：计算散布与反冲后的方向，在同次 `shoot()` 内完成地图射线、人物回溯和穿透，再产生 `shot` 事件；没有子弹飞行到墙面的计时。

`cs2-collision.trace` 的长点射线使用整条线段的轴对齐包围盒收集候选，再遍历窄相位。AK 最大范围约208m；即使首撞只有11–24m，抬枪后的包围盒仍可能覆盖大量远处地形。真实 PHYS 的108方位重复测得：

- 坡下某些方向约98,000候选，单条查询约31–33ms。
- 黄车附近约92,000候选，查询约29–31ms。
- 实际30发AK的最贵方向单发约30–36ms，地图查询占96.8%–99.2%；10人native hitbox pose仅约0.35–0.51ms，穿透出口约0.05–0.07ms。

这超过60Hz单tick的16.7ms预算，是明确的服务器阻塞风险；它不是本轮已经观测到真实远程秒级延迟的证据。

已在 `.local` 准备等价加速候选：保留原遍历顺序、hull、窄相、skin与tie，仅对triangle-only子树/triangle primitive做保守线段包围盒筛选。不能直接拒绝hull：其plane交集不必严格落在顶点包围盒中，保留了反例。

compiled最贵查询约33.47→1.82ms、黄车约31.04→1.23ms；raw版本约45.89→8.31ms。真实方向、随机射线、每实现10000点射线及身体/radius/显式extents/support/rayIntervals对照均未发现差异。有限等价测试不等于全域证明；候选未应用，普通客户端与现有服务器仍用原查询。

## 弹孔延迟已排除与仍待确认的环节

已确认的调用链：本地预测枪口/后坐力表现；服务器结算后广播事件；client对events直接派发，`shotEffects.add()` 同步写实例矩阵并标脏。HUD弹数读取权威快照，native换弹也依赖权威reload状态；不能仅用“本地预测太快”解释权威换弹已到而弹孔未到。

两站各30发、本机WS回环对照未复现秒级补弹孔，换弹状态可见前事件已齐，接收至FX写入通常约0.1ms、提交为一帧级。穿透会产生多个同shotId事件，不能以事件数不等于30判吞弹；满弹孔环时实例数不增长也不代表没更新。

WT的state走datagram，shot/sound/ack走可靠有序control流。使用真实wire/parser和人为阻塞writer的纯CPU机制测试，能够产生“ammo0/reload快照新鲜，30发事件仍未到；放行后补到”的顺序。此测试人为制造阻塞，不能据此认定实际远程机器就是WT或网络丢包。WS同连接FIFO控制则没有这类状态越过旧事件的顺序。

下一步要以现场数据分流：

1. 最新received/applied state.time领先迟到shot.time数百毫秒以上：事件通道或应用处理队列偏斜。
2. 本地预测至authority事件很长、state与event同样旧：C2S输入、服务器处理或整体时钟进度。
3. 事件已及时处理，但FX至提交很长：客户端主线程/渲染提交。
4. FX和提交都及时而像素很晚/缺失：继续GPU呈现、深度/材质可见性排查；提交不等于像素可见。

## 按需采样

游戏地址添加 `?shotDiagnostics=1`（已有参数则加 `&shotDiagnostics=1`）。采样仅记录本人射击、权威状态、FX返回与下一渲染提交，默认关闭；没有新监听器、计时器、网络上传或游戏参数修改。数据有界并随导出的诊断JSON下载，不记录昵称/完整世界坐标。

远程机器在正常联机条件下复现一梭弹匣及延迟，立即按Esc，在“联机诊断”确认“射击链路采样已开启”，点击“导出诊断JSON”。保持原协议与画质，不先强制换WS来掩盖条件。导出会自动包含实际transport，无需人工记QUIC/WS。

`shot.at`是JSON解析后应用处理该事件的时刻，不是网卡收包时间；`submitted`是JS渲染提交返回，不是GPU完成或物理屏幕。只比较同一客户端performance时间，或同一服务器simulation时间；不相减两机performance时钟计算单向网延。记录、关联与重复检测有容量上限，摘要注明保留覆盖范围。

收尾发现主机网络已切换，先前LAN地址不再分配。本机localhost仍正常，未擅自改网络、证书或重启服务；现场采样前需重新确认双方在同一局域网及实际可联机地址。新入口已在localhost用正常TLS验证加载并校验SHA。
