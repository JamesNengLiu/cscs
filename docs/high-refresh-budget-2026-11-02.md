# 原计划第 18 项与第 8 项收尾：高刷预算和帧时间定位

以 main `1d38f86` 为基线，先保存源码散列并复测 1185 项自动化，再定位刷新节奏、CPU 和 GPU 三类因素。只修改客户端渲染预算、GPU 查询诊断和设置；不改变物理频率、rAF 调度、输入发送、弹道、后坐力、跳跃/疲劳、碰撞、镜头 A/B 或人物动作公式。保留 JS / Three.js / WebGL2，没有引入 Wasm、修改资源或重启现有 3001 服务。

## 定位证据

原生前台 Chrome，Apple M1 Pro，主屏窗口位置 `(0,0)`，1280×800、DPR 1；九个动画人物、实际客户端和离线权威 Game 经 IPC 运行。空场控制用同一窗口、真实 rAF、轻量 2D 画布。对照不使用模拟 120/144Hz 时钟，不连接现有房间。

- 空场和正常九角色都约 120Hz。空场 P99 约 9.1–9.3ms，正常游戏约 9.3ms，正常 GPU P95 约 .66ms、CPU P99 约 2.4ms。因此这批正常场景的尾部间隔波动不能归因为显卡饱和；仍包含浏览器/显示调度因素，尚未取得完整 OS 呈现轨迹来进一步归因。
- 旧策略必须同时满足平均间隔 >22ms、GPU 平均 >14ms 才降分辨率。在 120Hz 预算 8.33ms、144Hz 预算 6.94ms 下，实际超预算仍可能永远不触发。离线输入 `(帧20/GPU18)、(11/10)、(9/8)` 的持续压力均保持最高分辨率。
- 实际 GPU 压力也复现了此缺口：测试专用全屏着色器加入真实计时区间，固定两次提交，旧版整段平均约 100 FPS，GPU P95 约 18.8ms，分辨率始终为 1。此为人工 GPU 压力，不是地图正常负载或实体多机帧率。
- 原 GPU 查询暴露的是最近一次结果，控制器会把重复的旧结果作为新帧继续计入均值。旧 CPU 帧统计也不包含画质策略及分辨率重配的调用成本。本批修正这两处可观测性缺口。

## 局部实现

- 大厅和暂停菜单增加「自动画质性能目标」：自动 / 60 / 120 / 144 FPS，本机持久化；`?frameTarget=120` 可对当前标签页覆盖。目标用于渲染预算，不限制 rAF、不更改游戏规则或物理/输入频率。
- 自动目标仅在 CPU 和新鲜 GPU 查询均有明显余量时学习真实回调中位节奏。高负载掉帧不能把目标错误下调；更低的节奏须连续三个采样窗口确认。记录的是回调节奏，不认证屏幕物理刷新率。
- 按目标预算观察约两秒持续窗口，GPU P90 接近预算且实际回调超预算才逐档降世界画面分辨率。CPU 压力、纯调度波动及缺少 GPU 证据时保留清晰度。最小比例 .7、DPR 上限 1.25 及「优先流畅/优先清晰」固定档位保持，HUD 为原 DOM 清晰度。
- 发现并排除了切换引入的长帧：直接调用 `setPixelRatio` 在 GPU 压力下重配背缓冲，实测一次耗时约 31.8ms；单纯把调用前移到下一帧仍会停顿。最终自动调节复用已分配缓冲区，通过有效视口、scissor 与固定画布的裁切缩放映射回相同屏幕矩形，不增加复制通道、纹理或绘制批次。自动切换前后背缓冲尺寸保持不变；窗口尺寸变化、启动和手动提高容量才重配。
- 背缓冲保留当前窗口已分配的最高容量，降档减少实际着色像素，保留该缓冲显存；首次启动按所选档位分配。`drawingBuffer` 是实际分配尺寸，有效渲染尺寸单独看 `renderSurface.viewport`，不能将两者混为一谈。
- 降档间隔至少三秒；有足够 GPU 余量且 CPU 不紧张时，二十秒冷却后逐档恢复。暂停、失焦/时间中断、目标切换重新累计观察窗口。单次长帧不独自决定降档。
- GPU 查询仍异步轮询，最多四个待完成查询，不调用 `gl.finish()` 或像素读回。每个完成结果携带唯一序号、提交时刻、原分辨率和测量代次；重复、超龄、旧分辨率的查询不参与新预算判断。无扩展/断续计时保留手动质量能力。
- 帧诊断补充独立完成查询的 GPU 分布、回调启动延迟、画质决策开销和预算分类。GPU 分布最多保留最近 240 个有效查询，CPU 分布为最近 240 个渲染帧，两种窗口不保证一一对应；不把保留的最后一次 GPU 值当作均值。
- CPU 帧统计现在包括策略判断和分辨率重配成本；渲染提交仍单独测量。量化诊断不会替代实体显示或鼠标到光子的测量。

## 验证与复测

- `npm run test:render-surface`：原生两层 WebGL 与实际截图像素，验证四档缩放及恢复时的四角、中心、前景与 DOM 准星对齐，确认没有黑边或横向溢出。
- `npm run test:render-budget`：60/120/144 预算、CPU/调度限制造成的误降档保护、GPU 新鲜度/分辨率/序号隔离、冷却恢复、自动节奏学习、手动设置与窄 DPR、GPU 统计代次和存储故障。
- `npm run test:high-refresh`：真实 rAF 的空场、九角色、GPU 压力、CPU 压力和恢复对照。`FRAME_TEST_RECOVERY=1` 延长观察恢复；`FRAME_TEST_PASSES=2` 固定两次压力提交。测试压力代码只在路由夹具注入，不进入生产代码。
- `node tests/high-refresh-browser.mjs --before` 需要 `FRAME_TEST_BASELINE` 显式指向事先保存的旧 public 目录；不会用当前代码伪造旧结果。
- 模拟物理与 A/B 相机的 60/120/144/240Hz 金值回归保留；高刷预算纯逻辑覆盖 144Hz。实体 144Hz、低配 GPU、不同系统与真实多人设备仍待验收。

原始收据位于忽略的 `artifacts/high-refresh-*.json`；不提交截图、模型或本地收据。下文记录最终复测结果。

## 最终对照结果

下表均为同脚本、同窗口、相同两次人工全屏着色器提交。压力稳定阶段取最后两秒，整段包含约两秒的保守观察和切换过程；不能用稳定阶段数据隐藏初始降帧。

| 指标 | 修改前 | 最终方案 |
| --- | ---: | ---: |
| 正常九角色平均 FPS | 120.00 | 约 120 |
| 正常九角色帧间隔 P99 | 9.3ms | 约 9.3ms |
| GPU 压力整段平均 FPS | 100.28 | 约 115 |
| GPU 压力稳定阶段 FPS | 99.91 | 约 120 |
| GPU 压力稳定阶段 P99 | 17.5ms | 约 9.3ms |
| GPU 压力有效渲染比例 | 始终 1 | 1 → .85 |
| GPU 压力最大 CPU 帧 | 约 3ms | 最终复测 2.7ms（另一轮 3.5ms） |
| 正常场景绘制调用 | 74 | 74 |

自动恢复观察期 23 秒内，比例从 .85 恢复至 1；CPU 压力场景保持比例 1，未用降低清晰度掩盖主线程阻塞。中间被否决的画布重配原型产生约 34ms 长帧，最终视口方案消除了这次可复现的切换开销；原型收据单独保留，不能与最终方案混用。

正常场景、空场的 P99 仍约 9.3ms，超过严格 120Hz 的 8.33ms 预算。没有宣称已消除浏览器/屏幕调度波动，也没有宣称所有设备的 120/144Hz 均达标。实体 144Hz 与低配设备、真实多人无线环境的验收继续保留。

## 回归结论

最终源码完整自动化 **1213 通过、0 失败、0 跳过**，原 1185 项全部保留，新增 28 项。菜单持久化、标签页覆盖与窄屏布局 **13 项**通过；四档缩放及恢复的实际页面像素检查 **5 个场景**通过，包含世界四角、中心、独立前景层、DOM 准星与无横向溢出。

A/B 各七条路线的原生约 120Hz 轮跳均通过；B 的七路线 144Hz 模拟提交也通过，明确不是实体 144Hz 验收。主战武器 **4 组**即时射击场景、**7 组**武器/模式恢复，投掷物呈现 **9 项**、连续双闪 **5 项**、实际 QUIC/WSS **14 项**均通过。传输脚本包含软件渲染，不纳入性能表。

28 个受保护模块与修改前散列一致，覆盖服务端/Game、弹道与命中盒、移动/碰撞/疲劳、输入、预测、A/B 相机、枪械反冲、人物加载/骨骼和投掷物模型缓存。客户端从玩家状态读取到 GPU 提交前的整段模拟、镜头、反冲和动作代码逐字一致。没有用跳过绘制、改变模拟频率或提前执行武器动作来提高测试帧率。

最终性能收据为 `high-refresh-final.json`；`resize-diagnosis` 记录被否决的重配原型，`viewport-scale` 是复用视口的另一轮独立复测。单次本机 GPU 压力结果不外推为正常地图提升百分比，也不代表实体多人/所有设备保证。本批提交仅包含代码、测试与说明，素材和本地收据不纳入提交；现有 3001 服务未重启，前端刷新即可加载。
